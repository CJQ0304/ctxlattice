## 四、最重要的一条发现：**压缩与缓存是替代品**

边界轮只占 **10% 的轮次**（2/14/26/38），却吃掉了 **48.7% 的 billable token**。

原因是结构性的：A 臂（全量重发）**天生是纯追加的**，前缀缓存几乎 100% 命中，每轮只按全价付新增的那一点点；B 臂每 N 轮重写一次 F，那一轮前缀全废、整包按全价付。

于是有一个不太舒服的结论：

> **上下文压缩省下的 token，正是 provider 缓存已经替你打了 90% 折扣的那部分；
> 而为它付出的重建成本，是按 100% 全价支付的。**

这意味着两件事：

1. **在强缓存定价下（δ≤0.1），单会话内做压缩基本不划算**，甚至更贵。这不是实现缺陷，是价格结构决定的。
2. 真正能赢的场景只有三个，且都不是"单会话内多轮"：
   - **跨会话**（上一会话的前缀缓存本来就没法复用）；
   - **窗口溢出**被迫截断（此时 A 臂不是"更贵"，是"发不出去"）；
   - **provider 无缓存或缓存折扣很弱**（自建推理、部分国产模型）。

跨会话口径实测（每 8 轮一段，缓存冷启动）：good/40 轮 成本降幅 **+4.7%**，回本点提前到第 25 轮。方向对，但幅度说明——**光靠"换个存储"拿不到大收益，得靠"跨会话"这个前提成立**。

## 六之二、测量工具自身的两个缺陷（都已修，都值得记）

### 缺陷一：`-wal` 残留让 B 臂"提前回本"

首轮用 `--sqlite` 跑出 **36.3%**，而内存后端是 **21.9%**。查下来不是存储层的问题：
两个后端逐步 payload **完全一致**（第 2/13/14/20/26/38/40 轮 token 数与 F 体量逐项相同）。

真因在 bench 自己：清库时只删 `lattice.db`，**没删 `-wal` / `-shm`**。WAL 模式下残留的
`-wal` 会在下次打开时被当作未 checkpoint 的日志恢复，于是新一轮继承了上一轮的 plan 与轮次，
B 臂因此在第 20 轮就"提前回本"。

> 教训：**测量工具也是被测对象。** 一个把 21.9% 抬到 36.3% 的 bug 不会报错，
> 它只会让结论变得更漂亮 —— 而漂亮的方向恰恰是没人会去查的方向。
> 修法已进 `harness.py`：删库必连同 `-wal`/`-shm`，并留注释说明为什么。

### 缺陷二：估算路径字节/字符混用（**比缺陷一更危险**）

`cache_prefix_tokens` 的估算分支拿 **UTF-8 字节**公共前缀去除 `chars_per_token`，
而 `count()` 数的是**字符**。中文 3 字节/字 → `cached` 放大到约 3 倍 → 被
`min(·, gross)` 截到 `gross` → 几乎每轮 `billable = 0`。

后果不是"数字差一点"，而是**结论反向**：

| | `mode=exact`（字符，正确） | `mode=estimate`（字节，有 bug） |
|---|---:|---:|
| good · 输入降幅 | +21.9% | +24.0% |
| good · 成本降幅 δ=0.1 | **−4.3%** | **+20.0%** |
| bad · 成本降幅 δ=0.1 | −6.8% | +11.9% |

输入降幅只差 2 个点（估算本身的误差，可接受）；成本降幅差 **24 个点**，因为整个
δ 敏感性塌成了「成本降幅 == 输入降幅」——每一轮的"缓存命中"都显示 100%，
**包括边界轮**，而边界轮的前缀本该全废。§四那条最重要的发现（压缩与缓存是替代品）
正是靠"边界轮吃掉 48.7% 的 billable"支撑的，这个 bug 会把它整个抹掉。

> 教训与缺陷一同源、更狠：**它让结论从"不划算"变成"划算"，而且没有任何异常。**
> 从表上看，异常的表现是"成本那一列和输入那一列数值几乎一样"——一个看起来像
> "这两列本来就该差不多"的正常现象。

修法与防再犯：
1. 估算路径改为数字符、同取整（`ceil`），与 `count()` 严格同单位；
2. 新增 `tests/test_metrics.py`（10 条）只钉算术，最关键一条是语义不变量
   **纯追加轮的可计费量 == 本轮新增 token 数**；
3. 非 `exact` 口径时，报告顶部与终端输出**双重警示**，并明写
   「δ 敏感性表在这种口径下不可用于对外结论」——它衡量的正是被估算掉的那个量。

**修完之后的估算口径**（`bench/results/estimate-after-m1fix`）：

| | `exact` | `estimate`（修后） | `estimate`（修前） |
|---|---:|---:|---:|
| good · δ=0.1 | −4.3% | −1.6% | +20.0% |
| bad · δ=0.1 | −6.8% | −2.6% | +11.9% |
| none · δ=0.1 | −9.2% | −10.7% | −1.7% |

**符号回来了，档位排序也回来了**（good > bad > none 的降幅顺序与 exact 一致）。
绝对值仍有差（估算就是估算），但"结论方向"不再相反 —— 这是修这个 bug 判据的全部：
不要求估算精确，要求它**不许把结论说反**。

## 七、这份结果不能声称什么

1. **不能声称"生产实测"**：回复是回放的，不是模型生成的；语料真实、剧本有据，但结果类型是离线回放。
2. **不能声称"质量打平"**：没做保真核对。
3. **不能把 +21.9% 当"省钱"**：那是输入 token 降幅。省钱要看成本降幅，而它依赖 δ。
4. **不能只报 good 档**：`none` 是负的，`bad` 接近零，三档必须一起出现。
5. **不能声称这套能"让模型记得更多"**：它只改"回到同一件事的成本"，不改记忆容量。
6. **不能引用 `mode=estimate` 的数字**（哪怕它更好看）：估算口径在中文语料上会把
   缓存命中系统性放大，结论符号会反。要出数就装 `tiktoken`。
